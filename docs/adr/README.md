# Architecture Decision Records

Format: context → decision → consequences. An ADR is not changed; it is replaced by a new one that
marks it as `Superseded by ADR-XXXX`. One file per ADR is added when a decision
deserves its own discussion; for the MVP everything is in one place.

---

## ADR-0001 · Backend in Go

**Status:** Accepted · 2026-10-21

**Context.** The user explicitly asked for a Go backend. The platform is a long-living
process (runs from minutes to hours), with strong requirements on concurrency, graceful
shutdown and a small footprint.

**Decision.** The entire server side is Go (1.25+). No Python/Node services in the runtime path.
The frontend is Next.js, but it is a pure client (no server-side business logic except the BFF
proxy for cookies).

**Consequences.**
- (+) a single binary artifact, `CGO_ENABLED=0`, deployment without runtime dependencies
- (+) one goroutine per run, `context` through the whole chain, natural cancel/timeout
- (+) `go test` + testcontainers cover integration without a special framework
- (−) the LLM ecosystem is Python-first; SDKs are missing → we write thin HTTP clients
- (−) code generation (oapi-codegen, sqlc) requires discipline in CI

## ADR-0002 · Postgres as a queue (River)

**Status:** Accepted

**Context.** We need a durable queue for agent runs with retry, unique jobs and
the ability for a job to survive a restart. Redis and Kafka are additional infrastructure.

**Decision.** [River](https://riverqueue.com) — a job queue in Postgres, in the same database as
the run state.

**Consequences.**
- (+) enqueue and state change are **one transaction** — no "run created but job
  lost"
- (+) less operational surface (no additional broker)
- (−) the queue loads the primary database; above ~500 jobs/s the queue database should be split off
- (−) the Zookeeper/Kafka ecosystem (replay, partitions) is not available — not needed for the MVP

## ADR-0003 · SSE instead of WebSocket

**Status:** Accepted

**Context.** The live log and run status are one-way (server → client). WebSocket carries a
two-way protocol, its own heartbeats and a problem with proxies.

**Decision.** Server-Sent Events, with `Last-Event-ID` replay from `run_events`.

**Consequences.**
- (+) works through standard HTTP proxies and load balancers (`X-Accel-Buffering: no`)
- (+) reconnect and replay are part of the protocol, not our invention
- (+) tested with plain `httptest`
- (−) one-way — all commands go through REST (which is also the wish: no hidden channels)
- (−) HTTP/1.1 limit of 6 connections per domain in the browser → use HTTP/2 in production

## ADR-0004 · Sandbox per run

**Status:** Accepted

**Context.** The agent executes code generated by the model. A mistake in isolation is an
incident, not a bug. A shared workspace between runs is not acceptable.

**Decision.** One ephemeral sandbox (Docker container / K8s Job) per run; it is destroyed
mandatorily; artifacts are extracted before destruction.

**Consequences.**
- (+) the blast radius is one run; no state leaking between tasks
- (+) reproducibility: `sandbox_image` + `base_commit` + `run_events` = the same result
- (−) cold start of 2–4 s per run → warm pool in production (phase 2)
- (−) higher infrastructure cost than a shared runner

## ADR-0005 · OpenAPI-first + oapi-codegen

**Status:** Accepted

**Context.** Frontend and backend are developed in parallel; agents write a large part of the code and
are prone to "inventing" DTOs.

**Decision.** `api/openapi.yaml` is the source of truth. The server interface and types are generated;
only handlers and domain types are written by hand. `openapi-diff` blocks breaking changes.

**Consequences.**
- (+) no drift between documentation and code; the TS client is generated
- (+) contract tests are trivial (validation against the schema)
- (−) a slower iteration cycle for experimental endpoints → experiments go into
  `internal/` without exposure, then are promoted to OpenAPI when they stabilize

## ADR-0006 · Tenancy through `org_id` + RLS

**Status:** Accepted

**Context.** Multi-tenant SaaS; leaking data between orgs is the worst possible bug.

**Decision.** `org_id` on every tenant aggregate, required in every query, **plus**
Postgres RLS as a second line of defense (`SET LOCAL app.org_id` per transaction).

**Consequences.**
- (+) an application error does not leak data — the database refuses
- (+) the test for RLS is simple and required in CI
- (−) every transaction must set `app.org_id`; forgetting it is silent (0 rows),
  hence an integration test for every repo method
- (−) connection pooling must reset session variables (pgx `AfterConnect`/`RESET`)

## ADR-0007 · Git integration is provider-agnostic (GitHub + GitLab)

**Status:** Accepted · 2026-10-21

**Context.** Some customers run GitHub, others GitLab; agencies often have a mix
because the client owns the source host. A GitHub-only integration would make
the product unusable for a large share of the target market, and retrofitting a
second provider after the webhook and PR code exists is expensive.

**Decision.** The platform talks to git hosts through a `git.Provider` port
(`CreatePullRequest`, `ParseWebhook`). GitHub and GitLab are first-class
adapters in MVP; both are tested against fake HTTP endpoints. Provider-specific
details (App vs token auth, `iid` vs `number`, header names) stay inside the
adapter. The data model stores `repos.provider` and the provider-native ids.

**Consequences.**
- (+) adding Bitbucket/Gitea later is one adapter, no schema or API change
- (+) the UI shows "View on GitHub/GitLab" from one field
- (−) two auth flows to support and document (GitHub App vs GitLab token)
- (−) webhook verification differs per provider (HMAC vs shared token)

## ADR-0008 · Starter tasks live in the blueprint spec (schema v2)

**Status:** Accepted · 2026-10-22

**Context.** A blueprint that only sets the stack still leaves every project to
invent its first tasks, which is exactly the work the platform claims to
standardise. The v1 schema (docs/09) has no place to define them.

**Decision.** Add an optional `starter_tasks` array to the blueprint spec and
bump the schema to `"2"`; version `"1"` remains valid and means "no starter
tasks". Each entry is `{title, description?, priority?, acceptance?[]}` and is
validated server-side. Instantiation creates the project, then one task per
entry in `draft` state, so the team still runs them through the Definition of
Ready.

**Consequences.**
- (+) a new project starts with a real backlog instead of an empty list
- (+) tasks are normal tasks: Editable, gateable, assignable
- (−) the spec grows; blueprint versions must be immutable (already enforced)
- (−) instantiating is no longer a single insert (project + N tasks)
