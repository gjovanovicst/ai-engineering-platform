# v0.2.0 — 2026-11-22

**The UX and Assistant release.**

The platform stops being a place where you type commands and becomes a place you
work in: every form validates inline and closes cleanly, every run page guides
the next action, and the assistant reads the screen you are looking at, fills
the form you have open, and reads a screenshot you attach. The first pilot
proved the whole loop: a task went from a plan to a merged pull request.

## Highlights

### The assistant

- **It reads your screen**: the panel sends the route, the open drawer (its
  title and the unsaved state) and the form's fields with every message; "explain
  this" answers from what you see, never "I cannot see the UI".
- **It fills the open form**: a drawer registers its fields; `fill_form` proposes
  the values as a preview and the client writes them on confirm. The assistant
  never submits — the human still clicks Create.
- **It grounds "this run"**: `ui_context.selection` carries the ids from the
  route, so "make a task from this failed run" reads the run instead of asking
  for an id.
- **It reads images**: attach up to five (a thumbnail with a remove); the model
  reads them with the text.
- **Message actions**: hover for copy; your message offers edit (the history
  truncates to it) and the answer offers retry.
- **It docks smartly**: on the right without a drawer, on the left beside one,
  above it without stealing the space.
- **Slash commands** (`/help`, `/triage`, `/standup`, …), a conversation history
  and a per-user rate limit.

### The forms

- **Four forms register with the assistant**: the task composer, the project
  create, the AI provider and the blueprint wizard.
- **Field options**: a select declares its allowed values (the task priority:
  low/med/high) — the model cannot write `medium` where the API expects `med`.
- **The UI contracts check**: `make web-check` runs a script that rejects a bare
  `window.confirm`/`window.prompt` and a drawer without a Close, so the classes
  of bug the pilot found cannot come back.

### The run and the review

- **A sticky primary action**, a timeline that tells the story, the cost and
  usage, the review and the checks in a hierarchy, and a mobile layout.
- **The design dialogs**: `ConfirmDialog` and `PromptDialog` replace the browser
  dialogs everywhere.
- **The patch-release mechanism**: the bug template v2, the severity and the
  backport labels, the `release/vX.Y` branches, the backport workflow and the
  nightly.

### The setup

- **Onboarding wizard** (`/setup`): the AI provider, the repository, the test
  command and the sandbox image, in four guided steps.
- **The command palette** (`⌘K`): create a task, start a run, navigate, open the
  settings, with recents.
- **The guidance layer**: a `NextAction` card on the run page and empty states
  that say what to do next.

### The pilots

- `gjovanovicst/pilot-go` and `gjovanovicst/pilot-web`, both registered with a
  repository, a test command and a sandbox image.
- The first weekly run: planning → development → review → **PR #1 opened** →
  the human merged it.

## The pilot's findings, fixed in this release

The first weekly report recorded five friction items; all are fixed:

| Finding | Fix |
|---|---|
| `POST /projects` said "invalid JSON body" for `slug` | the 400 names the field |
| `PUT /test-command` took `command` but returned `test_command` | it accepts both |
| no `PATCH /projects` | added (name, description) |
| the sign-in limit was hardcoded | `AIP_AUTH_LOGIN_RATE` |
| the webhook needed a hidden manual step | `webhook_url` in the payload, the playbook has the steps |

## Upgrading from v0.1.1

```sh
git pull
make migrate-up      # applies 0082..0085
```

- Migrations: `0082` (`tasks.scope*`), `0083` (the assistant conversation
  store), `0084` (the assistant RLS), `0085` (the assistant grants). All
  additive; forward-only as always.
- New environment variables: `AIP_ASSISTANT_LLM_PROVIDER`, `_BASE_URL`,
  `_API_KEY`, `_MODEL` (the assistant's model) and `AIP_AUTH_LOGIN_RATE`
  (default `5`).
- The assistant needs an LLM provider: set the four `AIP_ASSISTANT_LLM_*`
  variables or the assistant answers "not configured" and the rest of the
  platform works.

## Known limits

- **Developer preview**: self-hosted only.
- **The assistant's provider is the environment's**, not the org's AI provider
  config (planned for v0.3.0).
- **The assistant never approves, merges or submits** — by design.
- **The webhook is a manual step** per repository (the platform stores the
  secret but cannot install the hook).
- **The sandbox needs the Docker socket** and the image's toolchain on `PATH`.
- **The PR body carries the five sections**; a missing one fails the test.
- **The pilot's first run opened the PR on the second attempt**: the first
  failed on `sh: go: not found` and a stale PAT — both fixed here.
